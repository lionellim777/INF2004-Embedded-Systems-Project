## Barcode work: preserve the fix

The full-A failure during line recovery was reproduced from an actual saved
capture. The sensor can reverse over barcode coordinates and then cross them
again. The old first-forward envelope retained stale optical data and could
join it to the new path. The v0.5.1 latest-crossing reconstruction fixed that
capture without weakening Code39 guards or inventing a letter/edge.

The RTOS target enables `BARCODE_WAVE_LAST_PASS=1` and
`BARCODE_WAVE_RECOVERY_OPTICS=1`. Legacy defaults remain separate. Acquisition
must continue through line recovery and turning. Actual sensor coverage and
barcode geometry still determine whether a complete frame is physically seen.
Do not pause sampling merely because Motion is seeking the line.

Read [the recross diagnosis/tests](testing/rtos-v0_5_1-recross-fix.md) before
changing waveform reconstruction or restoring an older teammate scanner.
Saved failed full-A and bend-Z fixtures are in`docs/testing/fixtures/`.

**Decoding and barcode command execution are separate.** The accepted RTOS AAZ
test deliberately configures Y/Z route actions as straight, so it can read Z
without executing a stop/turn command. The full A–Z mission-action mapping,
replacement/deferral policy and end-to-end execution remain with the barcode
execution member. Do not infer their completion from three decoded letters.

## What RTOS implementation actually runs

This is real µT-Kernel task scheduling, not just adding MQTT to a bare-metal
loop. It uses **`tron-forum/mtk3_bsp` pinned at
`15ed232c08f2d89e54e514db79de150e224307e3`**, with the single-core bridge adapted
from Justin's groundwork. It does **not** use the
`sirfonzie/mtk3smp-rp2040` fork, and core1 is not started. Whether the school
specifically mandates that fork or SMP is still unconfirmed; clarify with the
lecturer before claiming exact-port compliance or changing the architecture.

| Task | Priority | Requested stack | Responsibility |
| --- | ---: | ---: | --- |
| Motion |2 |4096B |Debounce/start gesture, course/recovery and permitted motor proposals |
| Decoder |4 |8192B |Drain capture queue and decode complete barcode frames |
| Network |8 |4096B |One Wi-Fi/lwIP/MQTT runtime and binary transport |
| Observer |9 |4096B |USB commands, diagnostics and stack/timing reporting |

Lower priority numbers run first. Stacks come from the32KiB kernel pool; do not
add them to BSS twice. Kernel allocations include128B extra context per task;
startup/IRQ stack is a separate4KiB reservation. Marker/watermark instrumentation
is diagnostic, not an MPU or a worst-case proof. Most waits are task delays;
do not introduce blocking peripheral loops into Motion or the ADC IRQ.

Key code is under`firmware/app/mission_rtos/`. Reused motion/course/waveform
algorithms remain under`firmware/app/robot_firmware/`. See the
[target README](../firmware/app/mission_rtos/README.md) for build/port details.

## Integration contracts: keep these owners

1. **Only `mission_rtos/board.c` writes PWM.** Modules propose motion; Motion
   arbitrates. `board_apply` checks the active token/stop gate. Do not bypass it
   with a new motor driver, raw GPIO writes or a network-start path.
2. Only physical GP20 may arm/start. Remote MQTT/USB may select while stopped
   and request STOP; they cannot start. A stop cancels a prepared start.
   Tokens1..65535 never recycle; exhaustion requires reset.
3. One ADC owner samples GP26/28/27 every500us (2kHz). The barcode12-reading
   filter preserves all ADC12 precision. Queue capture is every2ms into512
   entries of14B, keeping full time32 and both encoder32 values. Do not add a
   competing ADC loop or replace the encoder GPIO callback.
4. The40ms service guard is checked every5ms. Stops override all proposals,
   including stale queued work. No current RTOS obstacle/sonar module exists:
   putting a hand in front of the car is **not** an implemented obstacle stop.
5. All hardware/task access currently relies on core0 ownership/local IRQ
   exclusion. Packing fields with another task/IRQ writer needs a new reviewed
   synchronization contract; local IRQ exclusion alone is not an SMP lock.
6. Keep raw encoders modulo32. Use snapshots and bounded differences; do not
   reset ISR counters to simplify a distance message.
7. Values need units, range/resolution, validity, freshness and boot/run
   generation. Unavailable, invalid, no-echo and valid zero are distinct.
   Validate wide inputs before packing; truncation is not validation.
8. Repeated A events at different capture times are separate barcodes. Mission
   command execution needs an explicit replace/defer/stop policy while turning.

The [module handoff contract draft](rtos-module-handoff.md) expands these rules
and the owner decisions still needed. It is a proposal, not an agreement already
obtained from the team.

## What minimum-bit work is done, and what remains

The school change requirement covers application working data, flags, sensing,
queues, shared state and MQTT, not just message size. The submitted Tribunal1
document is preserved as a historical proposal; unsupported claims/ranges are
corrected in the implementation decision log, not retrospectively rewritten.

Three independent opt-in options default OFF:

- `RTOS_COMPACT_ADC_STATE`:12×ADC12 history, bounded sum/index/count;36→21B.
- `RTOS_COMPACT_CORE_STATE`: stopped baseline80→48B; acquisition coordination
  13 separate bytes→4B with the existing IRQ access rules.
- `RTOS_COMPACT_CONTROL_STATE`: Motion-owned flags/state; whole runtime
  1432→1312B compared with stage2. Motor arithmetic/timestamps stay unchanged.

Shell build counterparts are `ROBOT_COMPACT_ADC_STATE`,
`ROBOT_COMPACT_CORE_STATE` and`ROBOT_COMPACT_CONTROL_STATE`. ON for all three
with `ROBOT_FIRST_FAILURE_CACHE=ON` produces full-diagnostic v0.6-dev3.
The normal provisioning helper intentionally forces OFF/OFF/OFF/cache ON.

| Profile | Static BSS | Acceptance |
| --- | ---: | --- |
| Accepted v0.5.1 |207332B |Two physical AAZ passes; reference |
| Full-diagnostic v0.6-dev3 |207156B |176B total representation reduction; software verified only |
| v0.6-dev3-lean |173492B |Additional33664B omitted first-failure raw-cache feature; software verified only |

Omitting that duplicate raw cache is **not minimum-bit savings**. Lean keeps
attempt summaries/latest frozen waveform but cannot retrieve an earlier failed
raw capture after a later successful scan. Keep full diagnostics for initial
candidate acceptance. Task stacks/pool and MQTT schemas are unchanged.

## Wireless and physical workflow

The demonstrated course workflow starts directly on the car's standalone supply
with Mac USB disconnected. Fresh boot selects track mode by default, without
movement. The Mac runs the broker/helper on the same LAN; Pico W joins2.4GHz,
while the Mac may use another band on the same router. Broker IP can change.
`--reuse` is valid only when saved settings/image/current broker address match.

Wait for **Wi-Fi live**, idle/latched/fault0 and fresh diagnostics before a run.
Align GP28 on black tape and GP26 on white for at least one second, then use
physical GP20. Do not walk a Mac USB cable along the track. After stopping,
keep Pico power until **Scan diagnostics saved; waveform checksum verified**,
then use`q`/Enter to finish/save the helper. USB reconnect while still powered
can recover retained data; power cycling can lose it.

The earlier USB→car-power handoff rebooted the Pico and lost telemetry until
USB was reconnected. The cold-boot wireless procedure is demonstrated; the
underlying handoff failure is not proven fixed. The helper warns about silence;
do not treat silence as proof of a motor fault or MQTT reconnection. See the
[wireless startup record](testing/rtos-wireless-start.md), noting its earlier
"next run" text is superseded by the completed wireless acceptance linked above.
